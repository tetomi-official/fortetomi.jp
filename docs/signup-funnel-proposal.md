# QRから登録までの改善案 — 話し合い用

作成日: 2026-08-07 / 対象: TETOMI プレリリース中

この資料は「こうします」ではなく「こういう方法があるが、どれにするか」を決めるためのものです。
A〜E の5つを決めれば、そのまま作業に入れます。

**今日決めたいこと**

| | 議題 | ひとことで言うと |
|---|---|---|
| A | QRの行き先 | 読み込んだ人を、どの画面に落とすか ← **今回の犯人はここ** |
| B | 登録の入力項目 | 10項目を減らすか。学部はどこで聞くか |
| C | 確認メールの壁 | 大学メールを開けない人をどうするか |
| D | 計測と運営用の画面 | どこで人が止まったかを見えるようにするか |
| E | 登録しても何もできない件 | 公開前の今、登録する理由をどう作るか |

---

## 1. 何が起きたか

イベントでQRコードを見せて登録を呼びかけた。読み込んだ人はいたが、アカウント登録は0件だった。

最初の見立ては「QRの行き先がLPになっていて、どこで登録するのか分かりにくかった」。
**データベースを調べた結果、この見立ては裏付けが取れた**（次章）。登録フォームを送信した人がゼロなので、
人が止まったのは登録画面より手前だった。

ただしコードを読み直したところ、**止まる場所は他にもある**。入口を直せば人は流れてくるが、
その先で次の壁に当たる。今日はそこまで含めて決めておきたい。

---

## 2. 今わかっていること／わかっていないこと

### わかったこと（2026-08-07 時点。データベースを直接集計した実数）

**登録を試みた人数: 4人**（サービス開始以来の累計）
**確認メールを開いた人数: 4人（4人中4人、100%）**
**確認メールで止まった人数: 0人**

実際の登録者は、開始以来ずっとこの4人だけだった。

| 登録日 | 確認メール | その後 |
|---|---|---|
| 7/14 | 開いた | ログインあり |
| 7/17 | 開いた | ログインあり（最終 8/5） |
| 7/20 | 開いた | ログインあり（最終 8/2） |
| 8/5 | 開いた | ログインあり |

**8/6以降の登録は0件。イベント後に登録を試みた人は、1人もいない。**

（総アカウント数は49件だが、うち37件は動作確認用の一括投入とデモ用、8件は開発中の検証用。
上の4人はそれを除いた実数。集計方法は末尾の付録）

### この数字が意味すること

**止まったのは「登録画面の登録ボタン」より手前。**
登録フォームを開いて送信した人がゼロなので、

- **議題A（入口）が今回の犯人**。QRを読んだ人が登録画面にたどり着けていない
- **議題C（確認メール）は今回の0件の原因ではない**。ただし通過した4人は落ち着いた環境で登録した人で、
  イベント会場の立ち話とは条件が違う。「今回の犯人ではない」だけで、問題が無いと確認できたわけではない
- 議題B（フォームが10項目）も、そもそもフォームに到達していないので今回は無罪。ただし
  **入口を直して人が来るようになった瞬間に、次の壁として効いてくる**

### それでもわからないこと（今は仕組みが無い）

- QRを読んだ人が何人サイトに来たか
- 登録画面まで来た人が何人か
- 登録フォームのどこで手が止まったか

アクセス解析の類は一切入っていない（GAもVercelのものも無し）。
「登録画面に来たが埋めずに帰った」のか「そもそもトップページで帰った」のかは、今は区別できない。→ 議題D

## 3. 止まる場所は4つある

### 止まる場所① 登録の入口が、ほぼ存在しない

サイト全体で新規登録ページへのリンクは**1箇所だけ**。しかもログイン画面の一番下。

- トップページの大きなボタンは「教科書を探す」「今すぐ出品する」の2つだけ。登録の入口なし
- 画面上のメニューは、未ログインだと「ログイン」だけ。「新規登録」は無い
- ページ下部のリンク集にも登録は無い

QRを読んだ人が登録にたどり着く道が、実質できていない状態。

### 止まる場所② 登録フォームが10項目ある

名前 / 大学メール / 復旧用メール / パスワード / パスワード確認 / 大学名(固定) / 学部 / 学年 / 性別 / 規約同意。

イベント会場での立ち話で、スマホで最後まで埋めきる量ではない。
なお学年は、大学メールの先頭にある入学年のコードから自動で判別する仕組みが**すでにある**（登録時にそれで在籍期限を計算している）。つまり学年は聞かなくても埋められる。

### 止まる場所③ 大学メールの確認リンクを開かないと使えない

登録すると大学メール宛に確認メールが飛び、そのリンクを開くまでログインできない。
スマホで大学のGoogleアカウントにログインしていない学生は、**その場では完了できない**。
会場を離れれば、たいてい戻ってこない。

### 止まる場所④ 登録しても、今は何もできない

現在は公開前の段階（閲覧のみ）に設定してある。そのため登録した直後に見えるのは、

- 出品ボタン → 押せない。「現在プレリリース中のため、出品はまだご利用いただけません。」
- 購入ボタン → 「🔒 準備中です」
- マイページ → 全体が「🚧 マイページは準備中です」

にもかかわらず、トップページには「今すぐ出品する」の大きなボタンが出ている（トップページだけ公開段階の判定が入っていない）。
押すと「準備中」に着く。**期待させて裏切る形**になっている。

## 4. 決めたいこと

作業量は ざっくり 小＝半日 / 中＝1〜2日 / 大＝3日以上 の目安。

---

### A. QRを読んだ人を、どこに落とすか ← 今回の犯人。ここが最優先

#### A-1. QR専用の短いページを新しく作る（おすすめ）

`/join?src=event0807` のような専用ページ。3行の説明と、大きな登録ボタンだけ。

- 良い点: 読み込んだ直後に「何をすればいいか」が1画面で分かる。今後QRを配る機会が増えるなら、毎回使い回せる。`?src=` の部分を配る場所ごとに変えれば、どのQRから来たか分けて数えられる
- 悪い点: 新しいページを1枚作る手間
- 作業量: 小

#### A-2. 登録フォームに直行させる

QRの行き先を登録画面そのものにする。

- 良い点: 一番短い。作業もほぼゼロ
- 悪い点: サービスの説明が一切ないまま、いきなり10項目のフォームが出る。警戒されやすい
- 作業量: 小（設定だけ）

#### A-3. トップページのまま、一番上を登録主役に差し替える

「探す」「出品」を下げ、「アカウント登録」を一番上に大きく出す。

- 良い点: 既存のページを直すだけ。QR以外から来た人にも効く
- 悪い点: トップページは長い読み物になっているので、読み進めるうちに登録から離れやすい
- 作業量: 小

**補足**: A-1〜A-3 は排他ではない。どれを選んでも、**画面上のメニューとページ下部に「新規登録」を足す**のは別途やった方がいい（今はどこにも無い）。作業量: 小。

---

### B. 登録の入力項目と、学部をどこで聞くか

前提として、どの案でも共通:
- **性別と復旧用メールは登録時から外す**（あとで聞く）
- **学年は大学メールから自動で埋める**（すでに仕組みがある）
- パスワード確認欄は、入力内容を目で見られるようにすれば省ける

問題は**学部**。学部ごとに教科書を絞り込む作りなので、これが無いとサービスの中身が薄くなる。
一方で、選択肢を1つ増やすたびに離脱は増える。どこで聞くかが論点。

#### B-1. 登録時に4項目（名前・大学メール・パスワード・学部）

- 良い点: 登録が終わった瞬間から自分の学部の教科書が見える。あとで聞き直す画面を作らなくていい
- 悪い点: 4項目でも、まだ「フォームを埋める作業」に見える
- 作業量: 中

#### B-2. 登録は3項目。中に入った直後に学部を聞く1画面を出す（おすすめ）

- 良い点: 登録の段差が一番低い。一度中に入った人は、多少の入力なら答えてくれる
- 悪い点: その1画面で答えずに離れる人が出る。学部が空のユーザーが発生するので、出品・購入の直前にもう一度聞く仕掛けが要る
- 作業量: 中（登録画面の短縮＋学部を聞く画面の新規作成）

#### B-3. QRの着地ページで、先に学部を選ばせる

登録より前に「学部を選んでください」→「あなたの学部に◯冊あります」を見せてから登録ボタン。

- 良い点: **登録する理由を先に見せられる**。「登録しないと中身が見られない」を実感させてから登録に進ませられる。A-1（専用ページ）と組み合わせると自然
- 悪い点: 一番作りが大きい。学部別の冊数を未ログインでも出せるようにする必要がある（今は全学の合計だけ未ログインに出している）。冊数が0や1だと逆効果
- 作業量: 中〜大

---

### C. 確認メールの壁をどうするか

※ 2章のとおり、**今回の0件の原因はここではない**（登録した4人は全員リンクを開いている）。
ただし4人とも落ち着いた環境で登録した人で、イベント会場の立ち話とは条件が違う。
入口を直して人が流れ始めたときに効いてくる可能性は残っている。

#### C-1. 今のまま。案内の文章と画面を改善する

「大学のGmailを開いてください」を明確に書く、Gmailを開くボタンを置く、後からでも完了できると伝える、など。

- 良い点: 作業が小さい。すぐ出せる
- 悪い点: 根本は変わらない。スマホで大学のGmailに入っていない人は結局止まる
- 作業量: 小

#### C-2. 「Googleで続ける」を足す

大学のメールはGoogleのアカウントなので、Googleログインに対応できる。

- 良い点:
  - **1タップで登録が終わる**（名前とメールはGoogleから渡ってくる）
  - **確認メールが不要になる** — 今回いちばん怒っていそうな壁が消える
  - 中央大学のアカウントであることの確認も同時に済む
- 悪い点:
  - GoogleとSupabaseの管理画面での設定作業が先に必要。**これはコードでは代行できず、ご本人の作業**になる
  - 大学のアカウントで外部サービスへのログインが許可されているか、事前に確認が要る（禁止されている大学もある）
  - 既存のメール＋パスワードの人との併存を考える必要がある
- 作業量: 中（＋設定作業）

**この資料でのおすすめ**: 今回は C-1 で出し、C-2 は次の段階。理由は、設定作業の待ちで A・B・D 全部が止まるのを避けたいため。ただし**効き目が一番大きいのは C-2** なので、設定の可否だけは早めに調べておきたい。

---

### D. 計測と、運営用の画面

#### D-1. 今のデータを見る → **済み（2章の数字）**

`node scripts/report-signup-funnel.mjs` でいつでも取り直せるようにした。
次のイベントの後にもう一度これを走らせれば、施策の前後で比べられる。

#### D-2. QRのURLに `?src=` を付けて、登録完了まで持ち回る

配る場所ごとに `?src=event0807` `?src=poster_a` のように変え、その値を登録完了まで保持して記録する。

- わかるようになること: どのQRから何人来て、何人が登録画面まで進み、何人が登録を終えたか
- 作業量: 中

#### D-3. 数字を見るだけの運営用ページを作る

`/admin` のようなページで、登録数・確認完了率・学部別の内訳・どのQRから来たか・日付別の推移を表示する。

- 今の状態: 運営用の画面は存在しない。「誰が運営か」を判定する仕組みも無い
- ただし土台は揃っている: 特権的にデータを読むサーバー側の仕組みと、その使い方の実例がすでにある
- 運営の判定は、**環境変数に運営のユーザーIDを並べる方式**ならデータベースを変えずに済む
- 個人情報は出さず、数字だけにすれば扱いが軽い（今回はこれで合意済み）
- 作業量: 中

**おすすめの順番**: D-1（今日）→ D-2（次のイベントに間に合わせる）→ D-3。
D-2 が入っていないと、次のイベントでも「登録0件でした」以上のことが分からない。

### E. 登録しても、今は何もできない問題

これは導線の話ではないが、**登録0件の理由の一部**である可能性がある。

#### E-1. 「先行登録」だと明記して、何が得られるかを書く

「今は準備中です。先に登録しておくと、公開したときにお知らせが届きます」のように、
登録の見返りを登録画面と着地ページに書く。

- 作業量: 小
- 論点: **実際に何を約束するか**。お知らせを送るなら、送る仕組みと文面が要る（メール送信の仕組み自体はすでにある）

#### E-2. トップページの「今すぐ出品する」の扱い

今は押すと「準備中」に着く。公開前の間は、

- 文言を変える（例: 「出品の準備をする」）
- 隠す
- そのままにして、着いた先で丁寧に説明する

のどれにするか。作業量: 小

#### E-3. 公開段階をいつ上げるか

環境変数を 0→1→2 と上げるだけで、購入・出品が解禁される（コード変更不要）。
「登録者が◯人集まったら上げる」のような目安を決めておくと、Eの話が具体的になる。

## 付録: 数字の取り方（次回以降も同じ手順で取れる）

```bash
node scripts/report-signup-funnel.mjs
```

読み取りのみで、データベースには何も書き込まない。`.env.local` の接続情報を使う。

出るもの: 実際の登録者の一覧（登録日・確認メールを開いたか・その後ログインしたか）、日付別の推移、まとめの3数字。

**混ざりものの除き方**（このスクリプトが自動でやっていること）:

- 一括投入・デモ用（37件）— 名前が `bulk.` で始まるもの、および**同じ秒に5件以上まとめて作られた**もの。
  ログイン画面に出てくる `sato@g.chuo-u.ac.jp` などのデモアカウントはここに入る
- 開発者の検証用（8件）— メールに `+` が付いた別名、および大学ドメイン以外
- 残りが実際の登録者（4件）

**数字の読み方**:

- 「登録を試みた人数」が増えていないなら、止まったのは登録画面より手前 → 議題A（入口）
- 増えているのに「確認メールを開いた人数」が少ないなら → 議題C（確認メール）
- どちらも増えているのに使われていないなら → 議題E（登録しても何もできない）

なお同じことは Supabase の管理画面の SQL Editor でも取れる（ただし混ざりものは手で除く必要がある）。

```sql
select
  date(created_at) as 日付,
  count(*) as 登録を試みた人数,
  count(email_confirmed_at) as 確認メールを開いた人数
from auth.users
group by 1
order by 1 desc;
```
