## A. すぐ直したほうがよいもの

### A-1. 取引の通知が1通も飛んでいない 🔴 → 対応済み

**実際に確認したこと**: `app/sell/page.tsx:347` と `app/listings/[id]/page.tsx:393` は
画面に「出品者に通知されます」と書いている。しかし通知の実体は
[`lib/notifications.ts`](../lib/notifications.ts) のヘッダーのバッジ件数だけで、
**メールは1通も送っていない**（Resend を使っているのは再認証・アカウント復旧の3か所のみ。
予約・決済まわりには送信処理が存在しない）。

**何が起きるか**: 出品者はTETOMIを開かない限り購入希望に気づけない。買い手も承認されたことを
知れない。受け渡しの当日まで誰も気づかない、ということが普通に起きる。

**要るもの**: 購入希望が届いた／日程が確定した／決済が終わった の3点。
最低でも決済完了は、金額・手数料・受取額を書いて**買い手と出品者の両方に**送りたい。

**対応**: 5種類のメールを追加した（購入希望・日程確定・逆提案・取りやめ・決済完了）。
あわせて、予約の書き込みをサーバー経由（`app/api/reservations`）に変えた。
以前はブラウザが Supabase に直接書いたあと、別のリクエストで「送って」と頼む形だったため、
その間にブラウザが閉じるとメールが飛ばない隙間があった。いまは書き込みとメール送信が
同じリクエストの中で完結する。安全性の作りは変わっていない（サーバー側も anon キー＋
本人の Cookie で書くので、RLS も列権限もトリガーも同じに効く）。

### A-2. 「いつ請求されるのか」が買い手に伝わっていない 🔴 → 対応済み

**実際に確認したこと**: 購入希望の確認画面の文言は以下がすべてで、支払いに一切触れていない。

> 以下の内容で送信します。よろしければ「購入希望を送る」を押してください。
> [E2E] 線形代数入門 第3版 ¥1,200 受け渡し候補 9/12 昼休み 9/13 昼休み 希望場所 Forest Gateway 3F

カード登録画面（`/checkout`）にも「登録しただけでは請求されない」旨の記載が無い。
説明があるのは [`components/PaymentQR.tsx:95`](../components/PaymentQR.tsx) の
QRを出す画面だけ（「読み取られると決済が完了します」）。

**何が起きるか**: 買い手は「購入希望を送った＝買った・請求される」と思い込む。
カードを登録した時点で請求されたと思う人も出る。問い合わせと不信の元になる。

**要るもの**: 購入希望のモーダル（入力・確認の両方）とカード登録画面に、
「いま請求は発生しません。受け渡しの場で出品者がQRを読み取ったときに決済されます」に
あたる一文。

### A-3. 予約しても出品が押さえられない（二重売りになる） 🔴 → 対応済み

**実際に確認したこと**: 出品者が受け渡し日を確定して予約が `承認済み` になっても、
出品は `出品中` のままだった。`ListingStatus` に `予約済み` という値はあるのに、
**コードのどこからも書き込まれていない**（書き込みは
[`lib/payment-provider/reconcile.ts:63`](../lib/payment-provider/reconcile.ts) の `完了` だけ）。

**何が起きるか**: 承認済みの取引がある本が一覧に残り続け、別の人からも購入希望が届く。
出品者は1冊しか持っていないのに複数人と受け渡しの約束をしてしまう。

**要るもの**: 承認時に出品を `予約済み` にする。キャンセル時は `出品中` に戻す。
併せて、`予約済み` の出品に新しい購入希望を受け付けないようにする（DB側の歯止めも）。

### A-4. 支払わずに「完了」にできてしまう 🔴 → 対応済み

**実際に確認したこと**: 買い手のアカウントから
`reservations.status` に直接 `完了` を書き込めた（決済の記録は無いまま）。
`reservations.status` には CHECK 制約も遷移チェックも無く、`status` 列の更新権限が
当事者に開いているため。遷移ルールはマイグレーションのSQLコメントにしか書かれていない。

**何が起きるか**: 悪意があれば、支払わずに取引を完了扱いにできる。
悪意がなくても、状態がおかしくなったときに誰も気づけない。

**要るもの**: 遷移ルールを1か所（例 `lib/reservation-flow.ts`）に置き、
DBのトリガーと画面の両方がそれを見るようにする。`完了` はサーバー（決済成立）からしか
書けないようにする。単体テスト `lib/__tests__/reservation-flow.test.ts` に期待する遷移表が
書いてあるので、それを通す形で作ればよい。

### A-5. 受け渡し前のキャンセルができない 🟠 → 対応済み

**実際に確認したこと**: `承認済み` の取引で画面に出るボタンは、
買い手側が「受け取り・支払いへ」、出品者側が「QRを読み取って決済」のみ。
**取りやめる手段がどちらにも無い。**

**何が起きるか**: 買い手が行けなくなった・本が別で手に入った、といったときに逃げ道が無い。
`承認済み` のまま放置された取引が溜まる（出品も押さえられていないので状態が読めなくなる）。

**要るもの**: 受け渡し前（未決済）のキャンセルボタン。押したら出品を `出品中` に戻し、
QRの合言葉も消す。

## B. 実態と食い違っている表示（信用に関わる）

### B-1. マイページの「売上残高」と「振込申請」が実態と違う 🟠

[`app/mypage/page.tsx:588-637`](../app/mypage/page.tsx) は「売上残高（受取見込み）」を表示し、
無効の「振込申請」ボタンと「振込手数料 ¥250／回」を出している。

しかし Stripe Connect では**決済と同時に出品者のStripe残高へ送金済み**で、TETOMIは
売上金を預かっていない。振込申請という手順も、250円の振込手数料も存在しない
（`PAYOUT_FEE_YEN` は Stripe の課金経路では一切使われていない）。`payouts` テーブルも無い。

今回の実測では、決済した瞬間に出品者のStripe残高へ ¥1,080 が入り、
引き出し可能日（2026-09-19）が付いた。入金サイクルは毎週金曜・4日遅れ。

**要るもの**: この表示を「Stripeの残高を見に行く導線」に置き換えるか、
Stripe APIから実際の残高と入金予定日を取ってきて表示するか。どちらにするかは方針次第。

### B-2. 法定ページが PAY.jp 前提のまま 🟠

利用規約 第11条2項（振込手数料250円）・第12条（売上金の管理および振込 全6項）、
特商法ページ、プライバシーポリシー（「PAY株式会社（決済処理・売上金振込）」）が、
いずれも「運営が売上金を預かる」前提の文面になっている。

[`docs/stripe-legal-review.md`](./stripe-legal-review.md) に整理済みだが未対応。
**規約に書いてあるのに実際には取らない／やらない**状態で、公開前に直しておきたい。

## D. 正しく動いていたもの（記録）

- 出品（写真2枚必須・必須項目のバリデーション・学部横断の保存）
- 購入予約（候補日1〜3件・場所の既定値・価格の突き合わせ）
- 日程調整（候補からの確定・逆提案→承諾・**買い手が確定や逆提案をできないこと**）
- カード登録（**3Dセキュアを要求していることをStripeの記録で確認**：`request_three_d_secure=any`、結果 `attempt_acknowledged`）
- カード登録だけでは課金されないこと
- QRの発行（承認前は409・買い手以外は403・**入金先が未設定の出品者は409**）
- QR読み取りでの決済（`paid_at`・`charge_id`・`payment_intent_id` の記録）
- **二重読み取りの防止**（2回目は409、Stripe側の成立も1件だけ）
- **手数料の計算**（¥1,200 → 手数料 ¥120 → 出品者 ¥1,080。単体テストで0〜5,000円の全額について1円もずれないことを確認）
- 出品者への送金と入金予定額（残高 ¥1,080 / 引き出し可能 2026-09-19 / 毎週金曜の入金サイクル）
- 決済後に出品が `完了` になり一覧から落ちること
- Webhookの二重記録防止と署名検証（署名違いは400）
- 申請中・日程調整中のキャンセル（買い手・出品者の双方から）
- キャンセルした取引のQRでは決済できないこと
- 返金（カードへの返金・出品者への送金の巻き戻し・手数料の返却まで実データで確認）
