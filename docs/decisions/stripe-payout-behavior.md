# 出品者への入金の実際の動き（実測）

作成日: 2026-09-21 / 対象: issue #54（タスク9）/ 関連: `docs/decisions/stripe-legal-review.md`

マイページに出ている「振込申請」ボタンと「振込手数料 ¥250／回」が実在しないので、
**実際は何がどう動くのか**をテストモードで測った。タスク10（法定ページの文言）と
タスク16（本番チェックリスト）はこの結果を前提にしてよい。

測定に使ったもの:

- テストキー（`sk_test_`）。本番の金は一切動いていない
- 連結アカウント `acct_1UCWMb9DOCi4eK24`（JP・individual・Express・`transfers` のみ有効）
- 実行日 2026-09-21（月）。この日は敬老の日で、9/22・9/23 も祝日。次の営業日は 9/24（木）

---

## 分かったことの要点

1. **任意振込（手動の振込）は技術的にできる。着金は 9/21 → 9/25（金）だった**
2. **1回振り込むごとに 0.25% + ¥250 が運営に請求される。** 出品者ではなく運営の負担
3. **それとは別に、入金があった出品者1人につき月額 ¥200 も運営の負担**
4. **Stripe 側に最低振込金額が無い。** ¥1 の振込も通った＝出品者が¥1ずつ押すと運営が¥250ずつ払う
5. いまの設定は**毎週金曜の自動入金**。運営が何もしなくても出品者には自動で届く

---

## 1. 任意振込の操作から着金まで何日か

`POST /v1/payouts` に `Stripe-Account` ヘッダーを付けて、連結アカウントの残高から振込を作った。

| | 値 |
|---|---|
| 振込ID | `po_1UI1jG9DOCi4eK24pVegwcg8` |
| 金額 | ¥10,000 |
| 作成 | 2026-09-21 16:33（JST・月・祝日） |
| `arrival_date` | 2026-09-25（金） |
| `method` | `standard` |
| `automatic` | `false` |

**入金サイクルが「毎週金曜の自動入金」のままでも、手動の振込は作れる。** スケジュールを
`manual` に切り替える必要はなかった。

Stripe のドキュメント（`stripe docs /payouts`）では、手動の振込は
**「開始してから着金まで通常 1〜4 営業日」**。同日着金はアメリカ・イギリス・ユーロ圏だけで、
日本は対象外。今回の実測（祝日3連休の最終日に操作 → 次の営業日の翌日に着金）はこの範囲に収まっている。

つまり**画面に「何日後」と断定して書けない**。書けるのは Stripe が返す `arrival_date`（入金予定日）そのもの。

### 残高が使えるようになるまで（振込とは別の話）

決済で出品者の残高に入った金は、すぐには振り込めない。`balance_transactions` を見ると、
9/20・9/21 に発生した売上はすべて `available_on = 2026-09-30`（＝ 4 営業日後）で `pending` のまま。

ドキュメントの日本の欄も **初回7暦日・以降4営業日**で一致した。
日本は営業日カウント（祝日を除く月〜金）。

## 2. 0.25% + ¥250 は誰に請求されるか

**運営（プラットフォーム）に請求される。** Stripe の料金ページ（stripe.com/jp/connect/pricing）の
「料金体系は貴社が管理」プラン — TETOMI はこれに該当する — の記載:

| 項目 | 金額 | 負担 |
|---|---|---|
| 月額アカウント料 | ¥200（有効なアカウントごと・月額） | 運営 |
| 入金手数料 | 0.25% + ¥250（入金ごと） | 運営 |
| 送金手数料 | 入金額の 0.25% | 運営 |
| 決済手数料 | 3.6%（+ 消費税） | 運営 |

「有効なアカウント」＝**その月に銀行口座への入金があったアカウント**。
請求は都度ではなく月末にまとめて来る。

TETOMI が「貴社が管理」側なのは残高取引で裏が取れた。¥2,000 の取引1件の運営側の内訳:

```
charge          +2,000   fee 79（Stripe決済手数料 72 + 消費税 7）
transfer        -2,000   （出品者へ送金）
application_fee   +200   （TETOMI のサービス手数料 10%）
                 ------
運営の手取り       +121
```

### テストモードでは手数料が付かない（ここは注意）

実際に振込を作っても、連結アカウント側の `payout` 取引は `fee 0`、運営側にも手数料の
取引は1件も出なかった。**テストモードは入金手数料を計算しない。**
なので「0.25% + ¥250 が引かれる瞬間」は実測できていない。上の表は Stripe の料金ページが根拠。
本番の初月に、月末の請求で実額を確認すること。

### 採算がどうなるか

1人の出品者が1か月に1回入金を受ける前提で、価格ごとに計算するとこうなる。

| 販売価格 | 運営の手数料収入(10%) | Stripe決済手数料(3.96%) | 送金0.25% | 入金 ¥250+0.25% | 月額 ¥200 | 運営の残り |
|---|---|---|---|---|---|---|
| ¥1,000 | +100 | −40 | −2 | −252 | −200 | **−394** |
| ¥2,000 | +200 | −79 | −5 | −254 | −200 | **−338** |
| ¥5,000 | +500 | −198 | −11 | −261 | −200 | **−170** |
| ¥10,000 | +1,000 | −396 | −22 | −272 | −200 | **+110** |

**採算が合うのは1人あたり月 ¥8,000 くらい売れたときから。** 中古教科書1冊の値段では
赤字になる。これは任意振込を足すかどうか以前に、**今の毎週自動入金のままでも起きている**。

> これはこのタスクの範囲を超える話なので、ここに事実だけ残す。手を打つとしたら
> 入金の間隔を毎週→毎月にする（`interval: monthly`。入金回数が最大 1/4 になる）、
> サービス手数料の料率を見直す、料金プランを「Stripe が管理」側に変える、のいずれか。

## 3. 手動入金に切り替えた場合の安全網

**切り替える必要は無い、というのが実測の結論。**

- 手動の振込は、入金サイクルが `weekly` のままでも作れた（1. のとおり）。
  つまり「自動入金を止めて手動にする」という二者択一ではない
- 自動入金を止めると、ボタンを押さない出品者の残高が放置される。日本は残高を
  最長90日で出金する必要があるため、催促の仕組みが要る。**止めない限りこの問題は起きない**
- 逆に自動入金を残したまま任意振込だけ足すと、**自動分と手動分で入金回数が増え、
  運営の ¥250 がそのぶん増える**

### 最低振込金額が Stripe 側に無い

¥1 と ¥100 の振込を作ってみたが、どちらも通った（`po_1UI1mp9…`／`po_1UI1mq9…`）。

**Stripe は最低金額を止めてくれない。** 任意振込を出すなら、TETOMI 側で最低金額を
設けないと、出品者が¥1ずつ押すたびに運営が¥250払うことになる。

---

## 結論（2026-09-22 決定）

**任意振込はやらない。** 自動入金のままにする。

理由:

- 任意振込を押しても着金は1〜4営業日。いまの自動入金（毎週金曜）と比べて縮まるのは数日で、
  出品者が得るものが小さい
- そのわずかな速さと引き換えに、**運営のコストが出品者の操作回数しだい**になる。
  振込1回 ¥250 は金額に関係なく定額で、Stripe は最低金額を止めてくれない
- 自動入金を残す限り「押さない出品者の残高が放置される」問題は起きない

これを受けて決めたこと:

| | 決めたこと |
|---|---|
| マイページの「振込申請」ボタン | 消す（実在しない機能） |
| 「振込手数料 ¥250／回」の表示 | 消す（一度も徴収していない） |
| `PAYOUT_FEE_YEN`（`lib/constants.ts`） | 削除する。課金経路で一度も使われていない |
| マイページの残高表示 | 予約テーブルからの自前集計をやめ、**Stripe の実残高と入金予定日**を出す |
| 銀行口座の変更・入金履歴 | Stripe の画面（Express ダッシュボード）へ誘導する。`/sell/connect` と同じ扱い |

### タスク10（法定ページの文言）への申し送り

- 第11条2項の振込手数料 ¥250 は**削除**してよい。徴収する場面が存在しない
- 第12条は「出品者が申請する」形をやめ、**決済会社の入金サイクルに従って自動で入金される**形で書く。
  `stripe-legal-review.md` の2節の代替案がそのまま使える
- 「最低振込金額1,000円」「翌月末を目処」「1年以上申請がなければ自動振込」は**全部消す**。
  どれも存在しない
- 第9条（退会時の残高放棄）も、運営が預かっていないので実行できない。書き換えが要る

## なぜ手数料が運営に来るのか（前提の確認）

`defaults.responsibilities.fees_collector` を `application` にしているからではない。
Stripe のドキュメント（`stripe docs /connect/accounts-v2/connected-account-configuration`）に
こう書かれている。

> `fees_collector` は**ダイレクト支払い**についての設定であり、
> **デスティネーション支払いまたは支払いと送金別方式の場合、Stripe は常にプラットフォームから手数料を徴収する**

TETOMI はデスティネーション支払い（決済は TETOMI 名義、送金だけ出品者へ）なので、
**設定に関係なく請求先は運営で固定**。出品者に負担させるにはダイレクト支払いへ作り替えることになり、
決済上の売主が出品者本人に変わる（＝特商法の「販売業者」表記も変わる）。
`stripe-legal-review.md` 6節が「変更する場合は法務確認を挟むこと」と書いているのがこの話。

**このタスクで動かせるのは手数料の負担者ではなく、入金の回数だけ。**

## 実測に使った操作のログ

```
# 運営残高に使える金を用意（テスト用カード pm_card_bypassPending）
POST /v1/payment_intents  amount=60000 → pi_3UI1ir9DOCpk8H6700KPqDxr succeeded

# 連結アカウントへ送金 → 送金分は連結アカウントの「使える残高」に即反映された
POST /v1/transfers        amount=50000 destination=acct_1UCWMb9DOCi4eK24 → tr_1UI1j49DOCpk8H67FbUrILel

# 手動の振込
POST /v1/payouts          amount=10000 (Stripe-Account: acct_…) → po_1UI1jG9DOCi4eK24pVegwcg8
                          arrival_date = 2026-09-25 / status は程なく paid
POST /v1/payouts          amount=1   → 通った
POST /v1/payouts          amount=100 → 通った
```

注: 送金（`/v1/transfers`）で入れた金は連結アカウントの**使える残高に即入る**。
決済（destination charge）で入る金だけが 4 営業日待ちになる。測定の都合でこの差を使った。

テストアカウントには上記の残高と振込が残っている。テストモードなので実害は無い。
