# TETOMI 取引フローのテスト手順

作成日: 2026-09-12 / 対象: 出品 → 購入予約 → 日程調整 → 取引確定 → QR読み取り → 決済 → 入金

人（手で触る）とAI（自動テスト）の二重で確かめるための手順書。
**自動で見ている範囲**と**人が見るしかない範囲**をはっきり分けてある。

---

## 1. 準備

### 1-1. 環境変数

プロジェクト直下に `.env.development.local` を作る（`.env.local` より優先される。Git には上がらない）。

```
NEXT_PUBLIC_RELEASE_PHASE=3
MAIL_DRY_RUN=1
```

`NEXT_PUBLIC_RELEASE_PHASE` が無いと、段階解禁の仕組みで購入も出品も塞がれたまま
テストが進まない。`MAIL_DRY_RUN` が無いと、シードアカウント（実在しないアドレス）へ
本当にメールを送ってバウンスする。

### 1-2. DBマイグレーション

`docs/supabase-migration-15-reservation-status-guard.sql` が適用されていないと、
T11 / T26 / T27 が落ちる（ステータスの歯止めはDB側のトリガーで効いているため）。
適用は Supabase の SQL Editor へ貼り付け。詳細は
[`docs/manual-setup-checklist.md`](./manual-setup-checklist.md) の I-1。

### 1-3. 開発サーバー

```bash
npm run dev
```

### 1-5. Stripe のテストカード

| 番号 | 何が起きるか |
|---|---|
| `4242 4242 4242 4242` | ふつうに通る |
| `4000 0025 0000 3155` | カード会社が本人確認（3Dセキュア）を求める |
| `4000 0000 0000 9995` | 残高不足で断られる |
| `4100 0000 0000 0019` | Radar（不正対策）がブロックする |

有効期限は未来の日付なら何でもよい（例 `12 / 34`）。CVCも任意（例 `123`）。

### 1-6. ⚠ 本番のデータベースを使っている

`.env.local` の Supabase は**本番プロジェクト**を指している。テストで作った出品や予約は
本番のDBに入る。そのため:

- 自動テストが作るものは、出品タイトルが必ず **`[E2E]`** で始まる
- 手で試すときも、**タイトルの先頭に `[E2E]` を付ける**（後始末の目印になる）
- 後始末は `npm run test:e2e:cleanup`（何を消すか表示するだけ）→ `-- --yes` で実行

**決済まで進んだデータは自動では消さない。** Stripe 側に記録が残るため、DBだけ消すと
突き合わせができなくなる。返金して片付ける:

```bash
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID> --dry-run
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID>
```

## 2. 自動テストの動かし方

```bash
npm test          # 計算とルールの確認（速い。画面は使わない）
npm run test:e2e  # 画面を通した確認（10分ほどかかる）
```

E2E の便利なオプション:

```bash
npm run test:e2e -- T13        # 指定したケースだけ
npm run test:e2e -- --headed   # ブラウザを見えるように開く（動きを目で追いたいとき）
npm run test:e2e -- --keep     # 作ったデータを消さずに残す（あとでDBを覗きたいとき）
```

### 結果の読み方

| 印 | 意味 |
|---|---|
| ✓ 通った | 期待どおり |
| △ 未実装（想定内） | **まだ作っていない機能。落ちるのが正しい。** 直せば ✓ に変わる |
| ✗ 想定外の失敗 | 壊れている。要調査。`tests/e2e/artifacts/` に失敗時の画面が残る |
| ★ 直っていた | 未実装だったものが通った。テスト側の「期待失敗」の印を外す合図 |

## 3. 自動で見ている範囲・見ていない範囲

### 自動で見ているもの

画面の操作だけでなく、**DBの中身と Stripe の実データまで突き合わせている**。
「画面に成功と出たが実際は保存されていない」を見逃さないため。

### 自動では見ていないもの（人が見るしかない）

| 見ていないもの | なぜ | どこで見るか |
|---|---|---|
| **カメラでのQR読み取り** | ブラウザの自動操作でカメラに映像を流し込めない。決済の中身（サーバー側）は自動で通している | 手順 M-1 |
| **3Dセキュアの画面の見え方** | 出る・出ないがカード会社次第。認証を要求していること自体は Stripe の記録で自動確認済み | 手順 M-2 |
| **メールが本当に届くか** | 受信箱を見る仕組みが無い。送信の手前（宛先の決定・文面・通知APIの検査）までは自動で確認済み | 手順 M-3 |
| **Connect のオンボーディング** | Stripe の画面の作りが変わる。1回通せばDBに残る | 手順 M-4 |
| **実際の銀行入金** | テストモードでは着金しない。入金予定日までは自動で確認済み | 手順 M-5 |
| **スマホでの見た目・操作感** | — | 手順 M-6 |

## 5. 手動テストの手順

### M-1. カメラでQRを読み取って決済する

自動テストはカメラを飛ばしてサーバーを直接叩いている。**現場で本当に読めるか**はここで見る。

1. スマホ（またはPCの別ウィンドウ）で買い手 `kimura` にログイン
2. 承認済みの取引の「受け取り・支払いへ」からQRを表示
3. **別の端末**で出品者 `sato` にログイン → マイページ →「受け取った購入希望」
4. 「QRを読み取って決済」を押す → カメラの許可を出す
5. 買い手の画面のQRにカメラを向ける

**見るところ**

- [ ] カメラの許可を求める表示が出る。拒否したときに何が起きるか分かる文言が出る
- [ ] 画面の明るさ・手ぶれがある状態でも読み取れる（実際の受け渡しは屋内・立ち話）
- [ ] 読み取った瞬間から決済完了までの待ち時間が、相手を待たせて気まずくない長さか
- [ ] 決済が終わったことが**出品者と買い手の両方の画面で**分かる
- [ ] 買い手の画面は自動で切り替わるか（4秒おきに見に行く作りになっている）

### M-2. カード情報の入力と3Dセキュア

**いつ入力するのか**: 出品者が受け渡し日を承認したあと、買い手が「受け取り・支払いへ」を
開いた時点。購入希望を送る時点ではまだ入力しない。

各カードで `/checkout/<予約ID>` を開いて登録を試す。

| カード | 見るところ |
|---|---|
| `4242 4242 4242 4242` | [ ] 登録できてQRが出る |
| `4000 0025 0000 3155` | [ ] 本人確認の画面が出て、通すと登録できる。**途中でやめたときに日本語で分かる文言が出る** |
| `4000 0000 0000 9995` | [ ] 「残高が足りません」に相当する日本語が出る。コードや英語が出ていないこと |
| `4100 0000 0000 0019` | [ ] ブロックされたことが日本語で伝わる |

- [ ] どのカードでも、画面に500エラーやStripeのエラーコードがそのまま出ない
- [ ] カードを登録しただけでは請求されないことが、画面から読み取れる（→ 現状は書いていない）

### M-3. メール通知

自動テストは「通知APIが正しく動くか」までしか見ていない（`MAIL_DRY_RUN=1` で実際には
送らない。シードアカウントは実在しないアドレスのため）。**本当に届くかはここで見る。**

手順:
1. `.env.development.local` の `MAIL_DRY_RUN` を外す
2. 自分が受け取れるアドレスでアカウントを2つ作る（出品者役・買い手役）
3. 出品 → 購入希望 → 日程確定 → カード登録 → QR決済 まで通す

- [ ] 購入希望が届いたとき、出品者にメールが届く
- [ ] 日程が確定したとき、買い手にメールが届く（受け渡し日時・場所が正しい）
- [ ] 別日程を提案したとき、買い手に届く
- [ ] 取りやめたとき、相手に届く
- [ ] 決済が終わったとき、**買い手と出品者の両方に**届く
- [ ] 出品者宛のメールの「販売価格 − 手数料 = お受け取り額」が Stripe の記録と一致する
- [ ] 迷惑メールに入らない（`npm run test:resend -- 自分のアドレス` で到達性を確認できる）
- [ ] スマホのメールアプリで読んだときに崩れない

### M-4. 出品者の入金先の登録（Stripe Connect）

新しい出品者アカウントで1回だけ通す。

1. `/sell/connect` を開く
2. 「受取口座を登録する」から Stripe の画面へ
3. テストモードでは自動入力のボタンが使える
4. 戻ってきたら `/sell/connect` の表示が「利用可能」になる

- [ ] 途中でブラウザを閉じても、やり直せる
- [ ] 登録が終わるまで、その人の出品にはQRが出ない（買い手側で確認）
- [ ] 「売上・入金を確認する」から Stripe の画面に入れる

### M-5. 出品者への入金

- [ ] Stripe の出品者向けダッシュボードで、残高と入金予定日が見える
- [ ] 入金の予定（サイクル）が設定されている

> テストモードでは実際の着金は起きない。本番で最初の1件が着金するところまでは、
> 公開後に必ず実地で確認すること。

### M-6. スマホでの見え方

受け渡しはスマホで行う。少なくとも以下を実機で。

- [ ] QRが画面内に収まり、相手のカメラから読める大きさで出る
- [ ] マイページの「QRを読み取って決済」ボタンが押しやすい位置にある
- [ ] 購入希望のモーダルが画面からはみ出さない
- [ ] 電波が弱いときに二度押ししてしまわないか（押したあとボタンが無効になるか）

### M-7. 決済後の返金

```bash
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID> --dry-run
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID>
```

- [ ] 買い手のカードへ返金される
- [ ] 出品者へ送った売上が巻き戻る（出品者の残高が減る）
- [ ] 受け取った手数料が返る
- [ ] 予約が「キャンセル」に戻る
- [ ] **出品は「完了」のまま残る** → 再出品したいなら手で戻す必要がある（既知の不備）

### M-8. 在籍期限切れ

`profiles.enrollment_valid_until` を過去の日付にして確認する。

- [ ] 出品ができない（フォームの代わりに再認証の案内が出る）
- [ ] 購入希望が送れない
