# Stripe 運用手順（返金・チャージバック・不正対策）

作成日: 2026-09-06 / 対象: 決済会社が Stripe のとき

管理画面をまだ持っていないため、運営が手で行う操作をここにまとめる。

---

## 1. 返金

### 手順

```bash
# まず内容を確認（何も変更しない）
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID> --dry-run

# 全額返金
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID>

# 一部返金（例: 1000円だけ返す）
node --env-file=.env.local scripts/stripe-refund.mjs <予約ID> 1000
```

### 何が起きるか

- 買い手のカードへ返金
- **出品者へ送った売上を巻き戻す**（`reverse_transfer`）
- **受け取った手数料を返す**（`refund_application_fee`）
- 全額返金のときは予約を「キャンセル」に戻し、決済の記録を消す

### ⚠️ Stripe ダッシュボードから直接返金しないこと

ダッシュボードで返金すると、TETOMI 側のDBは「完了」のまま残る。
買い手には返金されているのに、画面上は取引成立のままという食い違いが起きる。
必ず上のスクリプトを使う。

### ⚠️ 巻き戻しに失敗する場合

出品者の Stripe 残高が不足していると、送金の巻き戻しが失敗する
（すでに銀行へ入金済みの場合など）。その場合は Stripe 側でエラーになるので、
**出品者と個別に話をつける必要がある**。放置すると返金額をこちらがかぶる。

### 出品の扱い

返金しても出品（listings）は「完了」のまま。再出品させるなら手で戻す。

## 2. チャージバック（不審請求の申し立て）

### 何が起きるか

買い手がカード会社に「この請求はおかしい」と申し立てると、**申し立てられた金額と
手数料 ¥1,500 がプラットフォーム（TETOMI）の残高から引かれる。**
出品者へ送った売上は**自動では戻ってこない**。

つまり1件あたりの損失は最大で「商品代金 + ¥1,500」になる。
¥3,000の本なら ¥4,500、手数料収入（1件あたり約¥192）の**約23件分**が消える。

### 検知

`charge.dispute.created` の Webhook を受けて、予約の `payment_status` を
`disputed` に記録し、サーバーログに `stripe webhook: dispute created` を出す。
**送金の自動巻き戻しは行わない**（すでに出品者が受け取った売上を、こちらの判断だけで
取り戻さないため）。

### 対応の流れ

1. Stripe ダッシュボードの「不審請求の申し立て」で内容と期限を確認する
2. 申し立ての理由を見る
   - **不正利用（fraudulent）**: カード登録時に3DSを通しているため、
     責任がカード会社に移っている可能性が高い。3DSの認証結果を証拠として提出する。
   - **商品が届かない（product_not_received）**: 対面受け渡しなので、
     受け渡し日時・場所・当事者のやりとり（メッセージ）を証拠として提出する。
   - **説明と違う（product_not_as_described）**: 出品時の写真・状態の記載・
     メッセージのやりとりを提出する。
3. 期限内に証拠を提出する（**期限を過ぎると自動的に負ける**）
4. 出品者に負担を求めるかを判断する（→ 規約に定めが無いため要整備。
   [`docs/stripe-legal-review.md`](./stripe-legal-review.md) の7を参照）

### 提出できる証拠の在り処

| 証拠 | 場所 |
|---|---|
| 受け渡しの日時・場所 | `reservations` の確定した候補 |
| 当事者のやりとり | `messages`（マイページのメッセージ） |
| 出品時の写真・状態 | `listings` |
| 3DSの認証結果 | Stripe ダッシュボードの該当の支払い |

## 3. Radar（不正対策）

Stripe の標準機能で、追加料金なしで動いている。既定のルールで明らかな不正はブロックされる。

### 推奨する追加設定

Stripe ダッシュボード →「Radar」→「ルール」で設定する。

| ルール | 目的 |
|---|---|
| 高リスクなら3DSを要求 | 怪しい取引だけ本人認証を挟む。全件に掛けると通常の取引まで止まるので、リスクが高いものに限る |
| 高額なら3DSを要求（例: ¥50,000超） | 教科書の相場から外れた金額は疑わしい |

**⚠️ ブロックのルールは慎重に。** 受け渡しの現場で課金が止まると、
買い手も出品者も何が起きたか分からず、その場で解決できない。
「ブロック」より「3DSを要求」を優先する。

### テストの仕方

テストモードでルールを1本足し、以下のカードで意図どおり動くか確認する。

| カード番号 | 挙動 |
|---|---|
| `4100000000000019` | Radar がブロックする |
| `4000000000009995` | 残高不足で拒否される |
| `4000002500003155` | オフセッションで本人認証が必要になる |

拒否されたとき、画面に**日本語の分かりやすい文言**が出ることを確認する
（[`lib/payment-provider/errors.ts`](../lib/payment-provider/errors.ts)）。
500エラーやコードがそのまま出てはいけない。

---

## 4. 出品者が売上を確認したいと言われたら

TETOMI 側には残高画面が無い（売上金を預かっていないため）。
出品者は `/sell/connect` の「売上・入金を確認する」から Stripe の画面へ入れる。
そこで残高・入金の予定と履歴・銀行口座の変更ができる。
